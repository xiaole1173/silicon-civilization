# 多智能体群聊基座设计（Base）

> 本文只描述**基座层**：让 N 个模型待在同一个会话里、共享/隔离上下文、流式显示、可审计。
> 具体玩法（狼人杀、规则怪谈）作为**场景插件**跑在基座之上。

## 1. 目标与非目标

**目标**
- 一个会话里放 N 个 agent，按频道收发消息，每个 agent 看到"它有权限看到的部分"。
- 上下文由基座统一装配：稳定前缀 + 只追加的历史 + 易变尾部，可预算、可裁剪、可审计。
- 思考与回答**流式显示且不闪烁**（一次写入、只追加、不重排）。
- 模型 / base_url / api_key 全部可在页面手动录入，密钥只在服务端。
- 所有消息、调用、usage 落盘，可回放、可体检。

**非目标（本期不做）**
- 不做多租户、不做用户系统、不做公网部署。
- 不内置具体玩法规则（那是场景插件）。

## 2. 核心抽象

| 抽象 | 含义 | 关键点 |
|---|---|---|
| **Session** | 一次群聊（一局） | 有 id、场景、seed、参与者、预算 |
| **Channel** | 频道（public / wolves / private:3 / scene:xxx） | 消息带 channel，agent 订阅 subset |
| **Agent** | 一个参与者 = 座位 + 模型配置 | 身份、私有记忆、预算 |
| **Message** | 一条消息（说、动作、系统事件） | append-only，带 seq/channel/sender/kind |
| **Turn** | 一次"轮到谁发言/行动" | 由调度器决定，不由 agent 抢 |
| **Event** | 审计事件（turn_start/usage/error…） | 与 Message 分开存，便于回放与统计 |

**上下文 = 订阅频道的消息投影**，而不是"把整个对话塞进去"。这就是狼人杀里"狼看不到预言家查验"的实现方式，也是群聊可行性的关键。

## 3. 上下文管理（核心）

装配顺序必须是：**稳定 → 追加 → 易变**

```
[system 稳定块]   角色设定 + 场景前提 + 能力 + 输出格式            (整局不变)
[history 追加块]  订阅频道的消息，按时间升序，只追加不重写          (每轮变长)
[tail 易变块]     当前相位 / 存活 / 死亡 / 上次错误 / 本次要求      (每次重算)
```

- **只追加**：历史消息一旦写入渲染结果就缓存字符串，绝不重新拼接（否则前缀缓存必 miss）。
- **预算装配**：每相位给 token 预算（如发言 6000 / 决策 2000），超预算时按优先级淘汰：先淘汰最旧的公共发言 → 再淘汰旁观消息 → 绝不淘汰"事实卡"。
- **裁剪要留痕**：每次裁剪记录 `context_trim`（丢了哪几条），可审计。
- **私有投影**：每个 agent 的 history 只包含它订阅的频道；身份/查验等只进它自己的 system 或 private 频道。

## 4. 流式显示（解决闪烁）

现状问题：轮询增量文件 + 重试时清空 + 每轮整段重渲染 → 闪烁、显示中断。

**基座做法**
1. 服务端 **SSE 推送**（`/api/session/{id}/stream`），不用轮询。
2. 每条消息有**稳定的 message_id**；渲染层只做"追加"，已完成的消息不再重绘。
3. 一个 turn 内的增量分两种：`thinking_delta` / `answer_delta`；重试用 `turn_restart` 事件表示，渲染层把它**渲染成一条新的尝试块**（带"第 2 次尝试"标签），而不是清空上一条 —— 这样"重复"变成可解释的历史，而不是闪烁。
4. 断线重连带 `last_seq`，服务端补发缺失片段。

## 5. 幻觉治理（长对话必做）

现象：对话一长，模型开始编造死亡、记错票型、张冠李戴。

**分层对策**
| 层 | 手段 | 效果 |
|---|---|---|
| 输入 | **事实卡**：每回合注入结构化事实（存活名单、已确认死亡、自己的查验、当前票型），只给结论不给长文 | 减少"记错" |
| 输出 | **结构化发言**：`{claim, target, evidence}`，系统校验"提到的座位是否存在""死亡信息是否与事实冲突" | 编造可检测 |
| 纠错 | 校验失败 → **打回重说**（不是直接判死），最多 2 次 | 给纠错窗口 |
| 机制 | 投票基于**结构化倾向**而非单句文本；单句口误不该直接决定出局 | 降低"一句话致命" |
| 度量 | 统计 `hallucination_rate`（可验证陈述的错误率），按模型出报告 | 变成可研究指标 |

**根本原则**：不要指望模型"记得准"，而是**每回合把该记的事实重新喂一遍**，并且让它"说错"有代价但不致命。

## 6. 模型接入（手动填写）

- 页面录入：名称 / 协议（chat|responses|anthropic）/ base_url / api_key / model / temperature / max_tokens；
- **按座位分配**（一局里 12 个座位可以是 12 个不同模型）；
- 连通性自检（真发一次请求，返回延迟与中文错误原因）；
- 密钥仅存服务端 `data/models.json`（已 gitignore），接口只返回掩码。

## 7. UI（从"后台"改成"聊天"）

布局参考 DSH：**左侧频道/会话列表 → 中间消息流（气泡 + 折叠的思考）→ 右侧成员与指标**。
- 消息气泡区分发言人（头像色块 + 座位号 + 模型名）；
- 思考内容折叠在气泡内，展开后可滚动；
- 私密频道有明确视觉标记（只有观察者能看到）；
- 顶部只留最少的状态（第几天 / 进行中 / 胜方），不堆指标卡；
- 指标收进右侧抽屉，需要时再展开。

## 8. 技术风险清单

1. **token 预算**：全量历史线性膨胀（已实测第 5 天单次提示词 1.3 万字），必须有预算装配。
2. **前缀缓存**：当前网关实测 `cached_tokens=0`（不缓存）；换厂商后要靠"稳定前缀+只追加"才能命中。
3. **成本与时长**：12 人局约 160 次调用，20 分钟级；批量实验需要并发与断点续跑。
4. **并发**：同相位内可并行发问（写同一个 log 要加锁或按座位分片写）。
5. **可复现**：seed + temperature + 模型版本 + prompt 版本都要固定并记录。
6. **供应商抖动**：超时/空响应/流中断要能重试、降级、并标记（不要把"模型没答"记成"模型答错"）。
7. **长跑存储**：日志会到 MB 级，需要按局滚动与索引（现在靠 JSONL 全量读）。
8. **密钥安全**：不落日志、不进 git、不返前端。
9. **多实例冲突**：同一端口/同一 data 目录并发写会互相踩（已遇到过一次服务未重启导致接口 404）。
10. **评价口径**：胜率之外要有人类可读的行为指标（违规率、幻觉率、合作率、发言长度分布）。

## 9. 迁移路径

- **P1（1–2 天）**：Session/Channel/Message 抽象 + SSE 流式 + 聊天式 UI 骨架；先跑"闲聊/讨论"场景验证基座本身。
- **P2（1–2 天）**：上下文预算装配 + usage 落盘 + 事实卡 + 结构化发言校验。
- **P3（2–3 天）**：把狼人杀迁成第一个场景插件；再上规则怪谈。
